# 설계 결정

각 결정의 이유와 근거, 다시 검토할 조건을 적습니다. "확인"은 실행해서 본 것이고, "판단"은 코드나 문서를 읽고 내린 결론입니다. 실제 Claude·OpenAI API로 확인한 항목은 아직 없으며, 아래의 확인은 모두 로컬 스텁이나 테스트 환경에서 한 것입니다.

## 구조

### WebFlux 대신 MVC에서 `Flux` 반환

- **이유:** pgvector와 대화 기록이 모두 블로킹 JDBC라 WebFlux로 얻을 것이 적습니다.
- **근거:** MVC에서 `Flux<ServerSentEvent>`가 청크 단위로 전달되는 것을 실제 HTTP로 확인했습니다(`ChatStreamIT`).
- **재검토:** 동시 연결이 많아져 스레드나 커넥션이 병목이 될 때.

### 메모리 advisor를 RAG보다 먼저 실행

- **이유:** 순서가 바뀌면 FAQ가 붙은 프롬프트가 대화 기록에 저장되고, RAG가 이력을 받지 못합니다.
- **근거:** 저장된 질문이 원문인 것을 테스트로 확인했습니다(`ChatServiceTest`).

### 후속 질문만 재작성

- **이유:** `CompressionQueryTransformer`는 이력이 없어도 항상 모델을 호출합니다. 첫 질문까지 재작성하면 호출 한 번과 그만큼의 지연이 낭비됩니다.
- **실패 처리:** 재작성이 실패하면 원래 질문으로 검색합니다. 답변 자체를 실패시키지 않기 위해서입니다.
- **대가:** 재작성이 조용히 실패해도 답변은 나옵니다. 그래서 `LiveApiIT`의 `followUpUsesHistory`는 원래 질문만으로는 검색되지 않는 질문을 씁니다.

### FAQ가 없을 때 질문을 유지

- **이유:** Spring AI의 기본 빈 컨텍스트 템플릿은 사용자 질문을 프롬프트에서 지웁니다. 인사에도 답할 수 없게 되므로 직접 만든 augmenter로 질문을 유지합니다.
- **근거:** 프롬프트 내용을 테스트로 확인했습니다.

## 스트리밍과 장애

### 스트림은 `done` 또는 `error` 하나로 종료

- **이유:** 응답 헤더가 이미 나간 뒤에는 HTTP 상태로 실패를 알릴 수 없습니다. 종료 이벤트가 하나로 정해져 있어야 클라이언트가 어느 쪽도 받지 못한 경우를 끊긴 연결로 처리할 수 있습니다.
- **보안:** `error.message`는 고정 문구입니다. 예외 내용을 클라이언트에 보내지 않습니다.

### `request-timeout` 대신 스트림 유휴 타임아웃

- **이유:** 처음에는 `spring.mvc.async.request-timeout`을 넣었지만, `Flux` 반환에는 적용되지 않았습니다. 1초로 줄여도 5.5초짜리 스트림이 끝까지 전달됐습니다. 업스트림이 멈추면 종료 이벤트 없이 무한정 대기하게 됩니다.
- **결정:** 요소 단위 `Flux.timeout`(기본 60초)을 쓰고 효과 없는 설정은 지웠습니다.
- **대가:** 재작성, 검색, 첫 토큰까지의 대기도 이 시간 안에 들어갑니다.

### Claude 호출 전체 타임아웃 10분

- **이유:** 설정하지 않으면 SDK의 60초 호출 타임아웃이 적용되어, 청크가 계속 오는 답변도 60초에 끊겼습니다.
- **근거:** 5초 간격 스트림이 기본값에서는 60.4초에 실패했고, 10분으로 바꾼 뒤에는 70.4초에 정상 종료했습니다. 10분에서 실제로 끊기는 것은 확인하지 못했습니다.

### 연결이 끊겨도 업스트림 호출은 계속됨 (알려진 한계)

- **현상:** 클라이언트가 연결을 끊어도 Claude로의 호출은 멈추지 않아 비용이 나갑니다. 로컬 스텁이 200초 동안 계속 스트리밍하는 것을 확인했습니다. 원인은 Spring AI 쪽으로 보이지만 소스까지 확인하지는 못했습니다.
- **결정:** 라이브러리를 고치지 않고 `consult.max-tokens`를 8000으로 낮춰 건당 낭비를 제한했습니다.
- **재검토:** Spring AI가 취소를 전파하게 되거나, 공개 트래픽이 생겨 비용이 문제가 될 때. SDK 스트리밍을 직접 호출하면 해결할 수 있습니다.

### 빈 assistant 메시지를 저장하지 않음

- **이유:** 텍스트 없이 끝난 응답도 빈 메시지로 저장됩니다. Messages API가 이를 거부하면 그 대화의 이후 턴이 모두 실패합니다.
- **근거:** 저장되는 것은 테스트로 확인했습니다. API가 거부하는지는 판단이며 실제로 재현하지는 못했습니다.

### 거부 응답은 `REFUSED` 이벤트로 처리

- **이유:** Spring AI 2.0.2의 옵션으로는 서버 측 `fallbacks`를 지정할 수 없습니다.

## 검색

### 임베딩에 메타데이터를 넣지 않음

- **이유:** 기본 `metadata-mode`는 해시까지 임베딩 입력에 넣습니다. 질문은 원문으로 임베딩하므로 검색 품질이 떨어지고 임계값 보정도 의미를 잃습니다.
- **근거:** 실제 요청 본문에서 해시가 사라지는 것을 확인했습니다(`RealBeansStubIT`).

### 해시에 `embedding-index` 포함

- **이유:** 해시가 내용만 보면 임베딩 방식을 바꿔도 옛 벡터가 조용히 재사용됩니다.
- **근거:** 데모와 실제 모드를 오가며 필요한 만큼만 재임베딩되는 것을 확인했습니다.
- **대가:** 데모의 벡터 계산을 바꿀 때는 값을 손으로 바꿔야 합니다.

### 빈 FAQ 파일과 임베딩 실패는 기동 실패

- **이유:** 빈 `[]`를 그대로 처리하면 FAQ가 모두 지워지고 모든 답변이 "확인할 수 없음"이 됩니다. 조용히 틀린 채 도는 것보다 기동 실패가 낫습니다.

### 데모 임베딩은 단어 안의 글자 2-gram

- **이유:** API 키 없이 실제 검색 경로를 보여 주기 위해서입니다. 측정 결과 공백을 지운 2-gram보다 단어 안 2-gram에 불용어 제거를 더한 방식이 나았습니다.
- **한계:** 의미 검색이 아니며, 무관한 질문이 걸리기도 합니다. README에 사례를 적었습니다.
- **임계값 0.20:** 지식 문서 기준으로 다시 쟀습니다. 정답 질문 10개의 최저 점수는 0.223(알람 101), 무관 질문 31개의 최고는 0.173이라 그 가운데를 골랐습니다. 무관 질문 둘(0.224, 0.236)은 정답 최저보다 높아 어떤 값으로도 정답을 잃지 않고는 거를 수 없습니다. 하나는 단어 일부가 겹치고(다이어트, 컨베이어의 '이어'), 하나는 바이그램 해시 충돌입니다.

## 보안과 설정

### 사용자 입력을 로그에 남기지 않음

- **이유:** 상담 내용에는 개인정보가 들어갈 수 있습니다.
- **근거:** 두 경로에서 실제로 새는 것을 확인하고 막았습니다.
  - 입력 검증 실패: `DefaultHandlerExceptionResolver`가 거부된 값을 WARN으로 기록했습니다. 로그 레벨을 올렸습니다(`ChatControllerTest`).
  - NUL 문자 입력: pgjdbc 예외에 전체 메시지가 포함됐습니다. `logServerErrorDetail: false`로 막았습니다(`ChatStreamIT`).
- **남은 위험:** 업스트림 오류 메시지가 입력을 포함하면 `ChatService`의 오류 로그에 남을 수 있습니다.

### API 키가 없으면 기동 실패

- **이유:** 프로퍼티 바인딩은 풀리지 않은 `${...}`를 그대로 키 값으로 전달합니다. 실제로 그 문자열이 외부 API로 전송되는 것을 확인했습니다.
- **한계:** 값이 있는지만 확인합니다. 빈 값이나 틀린 키는 잡지 못합니다.

### 범위에서 뺀 것

| 항목 | 추가할 시점 |
|---|---|
| 인증, rate limit, 대화 소유권 | 공개 배포 전 필수 |
| 대화 보존 기간 | 실제 사용자 데이터를 받기 전 |
| Flyway | 운영 DB가 생길 때 |
| hybrid search, reranking | 실제 임베딩으로 측정해 부족할 때 |
| 상담원 연결 연동 | 연동할 시스템이 생길 때. 지금은 안내 문구만 제공 |
