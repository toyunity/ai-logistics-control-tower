# 설계 결정

각 결정의 이유와 근거, 다시 검토할 조건을 적습니다. "확인"은 실행해서 본 것이고, "판단"은 코드나 문서를 읽고 내린 결론입니다. 실제 Claude·Gemini API로 확인한 항목은 아직 없으며, 아래의 확인은 모두 로컬 스텁이나 테스트 환경에서 한 것입니다.

## 구조

### MVC에서 WebFlux로 전환, 블로킹 호출은 `boundedElastic`으로

- **처음 결정:** pgvector와 대화 기록이 모두 블로킹 JDBC라 WebFlux로 얻을 것이 적다고 보고 MVC에서 `Flux<ServerSentEvent>`를 돌려줬습니다.
- **바꾼 이유:** 이후 붙일 MCP 서버(`spring-ai-starter-mcp-server-webflux`)가 WebFlux를 전제로 하고, 요청 스레드 수가 동시 요청 수를 따라 늘지 않게 하려는 것입니다. 코어(domain, application)는 동기 코드 그대로 두고 웹 어댑터만 바꿨습니다. 단건 응답은 `Mono.fromCallable(...).subscribeOn(boundedElastic())`(`Blocking.call`), 채팅은 `Flux.defer(...).subscribeOn(boundedElastic())`입니다. `subscribeOn`은 구독과 함께 `request(n)`도 그 스레드로 옮기므로 메모리 저장, 검색, 도구의 설비 호출이 Netty 이벤트 루프에서 시작되지 않습니다. 각 웹 슬라이스 테스트가 서비스 대역이 `boundedElastic-` 스레드에서 불렸는지 확인합니다.
- **대가:** JDBC와 설비 HTTP(RestClient)는 여전히 블로킹이라 스레드를 아낀 것이 아니라 Tomcat 요청 스레드에서 `boundedElastic` 풀로 옮긴 것입니다. 이 풀은 코어 수×10(이 머신 100개)이 상한이고, MVC에서도 채팅 중 이 풀이 100개까지 찬 것으로 보아 Spring AI 내부도 같은 풀을 씁니다(실행으로 관찰). 그래서 블로킹 작업 동시 실행 수가 그 상한에 묶이고 나머지는 큐에서 기다립니다. 세션은 `InMemoryWebSessionStore`라 서버 재시작 시 사라지고, 시작된 세션이 1만 개를 넘으면 새 로그인이 실패합니다(판단: 기본 설정 읽기).
- **오류 로그:** MVC의 `DefaultHandlerExceptionResolver`처럼 거부된 입력을 WARN으로 남기는 처리기는 WebFlux에 없어 그 로그 설정을 지웠습니다(입력 오류 로그 테스트가 설정 없이 통과). 대신 WebFlux 기본 오류 처리기가 처리되지 않은 500을 요청 경로와 쿼리, 예외 문구째 ERROR로 남기는 것을 테스트로 확인해, 쿼리로 자유 문자열을 받는 지식 검색도 `WebErrors` 대상에 넣었습니다.
- **측정(실행, 로컬 10코어, 가짜 모델, `WebStackMeasureIT`):** 같은 하네스를 전환 직전 커밋과 전환 후에 각각 두 번 돌렸습니다. 숫자는 서버 쪽 스레드 이름으로 센 것입니다.

  | 조건 | MVC(Tomcat) | WebFlux(Netty) |
  |---|---|---|
  | SSE 200개 동시(각 약 10초) 최대 스레드 | 요청 스레드 21~22, `boundedElastic` 100 | 이벤트 루프 10, `boundedElastic` 100 |
  | SSE 200개 완료 시간 | 12.4~12.5초 | 12.4~12.5초 |
  | 현황 조회 1,000건(동시 50, 설비는 같은 프로세스 시뮬레이터) | 847~1,035건/초, 요청 스레드 108~125 | 823~1,007건/초, 이벤트 루프 10 |

  처리량은 차이가 없고, 달라진 것은 동시 요청에 따라 늘던 요청 스레드가 이벤트 루프 10개로 고정된 것입니다. SSE는 MVC에서도 비동기로 처리돼 요청 스레드를 붙잡지 않았습니다. 두 스택 모두 `boundedElastic`이 상한(100)에 닿았습니다.
- **재검토:** 블로킹 작업이 `boundedElastic` 상한에서 밀리기 시작할 때. 그때는 JDBC 호출을 가상 스레드 실행기로 옮기는 것을 먼저 봅니다.

### 메모리 advisor를 RAG보다 먼저 실행

- **이유:** 순서가 바뀌면 지식 문서가 붙은 프롬프트가 대화 기록에 저장되고, RAG가 이력을 받지 못합니다.
- **근거:** 저장된 질문이 원문인 것을 테스트로 확인했습니다(`AssistantPipelineTest`).

### 후속 질문만 재작성

- **이유:** `CompressionQueryTransformer`는 이력이 없어도 항상 모델을 호출합니다. 첫 질문까지 재작성하면 호출 한 번과 그만큼의 지연이 낭비됩니다.
- **실패 처리:** 재작성이 실패하면 원래 질문으로 검색합니다. 답변 자체를 실패시키지 않기 위해서입니다.
- **대가:** 재작성이 조용히 실패해도 답변은 나옵니다. 그래서 `LiveApiIT`의 `followUpUsesHistory`는 원래 질문만으로는 검색되지 않는 질문을 씁니다.

### 관련 문서가 없을 때 질문을 유지

- **이유:** Spring AI의 기본 빈 컨텍스트 템플릿은 사용자 질문을 프롬프트에서 지웁니다. 인사나 상태 질문에도 답할 수 없게 되므로 직접 만든 augmenter로 질문을 유지합니다. 문서가 없어도 상태 질문은 도구로 답하라고 프롬프트에 적었습니다.
- **근거:** 프롬프트 내용을 테스트로 확인했습니다.

## 스트리밍과 장애

### 스트림은 `done` 또는 `error` 하나로 종료

- **이유:** 응답 헤더가 이미 나간 뒤에는 HTTP 상태로 실패를 알릴 수 없습니다. 종료 이벤트가 하나로 정해져 있어야 클라이언트가 어느 쪽도 받지 못한 경우를 끊긴 연결로 처리할 수 있습니다.
- **보안:** `error.message`는 고정 문구입니다. 예외 내용을 클라이언트에 보내지 않습니다.

### Reactor 예외는 스트림 안에서 이벤트로 바꾼다

- **이유:** 모델 호출이 스트림을 만들기도 전에 예외를 던지면 `Flux` 밖으로 새어 나가 SSE가 종료 이벤트 없이 끊깁니다. 호출을 `Flux.defer`로 감싸 동기 예외도 스트림 오류로 만들고, `onErrorResume`은 확인 카드(`action`)와 `Done`을 붙인 뒤 맨 끝에 둬서 실패하면 카드도 `done`도 나가지 않고 `error` 하나로 끝나게 했습니다.
- **근거:** 동기적으로 예외를 던지는 대역으로 `meta` 다음 `error`만 나오는 것을 확인했습니다(`AssistantPipelineTest`).

### `request-timeout` 대신 스트림 유휴 타임아웃

- **이유:** 처음에는 `spring.mvc.async.request-timeout`을 넣었지만, `Flux` 반환에는 적용되지 않았습니다. 1초로 줄여도 5.5초짜리 스트림이 끝까지 전달됐습니다. 업스트림이 멈추면 종료 이벤트 없이 무한정 대기하게 됩니다.
- **결정:** 요소 단위 `Flux.timeout`(기본 60초)을 쓰고 효과 없는 설정은 지웠습니다.
- **대가:** 재작성, 검색, 첫 토큰까지의 대기도 이 시간 안에 들어갑니다.

### Claude 호출 전체 타임아웃 10분

- **이유:** 설정하지 않으면 SDK의 60초 호출 타임아웃이 적용되어, 청크가 계속 오는 답변도 60초에 끊겼습니다.
- **근거:** 5초 간격 스트림이 기본값에서는 60.4초에 실패했고, 10분으로 바꾼 뒤에는 70.4초에 정상 종료했습니다. 10분에서 실제로 끊기는 것은 확인하지 못했습니다.

### 연결이 끊겨도 업스트림 호출은 계속됨 (알려진 한계)

- **현상:** 클라이언트가 연결을 끊어도 Claude로의 호출은 멈추지 않아 비용이 나갑니다. 로컬 스텁이 200초 동안 계속 스트리밍하는 것을 확인했습니다. 원인은 Spring AI 쪽으로 보이지만 소스까지 확인하지는 못했습니다.
- **결정:** 라이브러리를 고치지 않고 `controltower.max-tokens`를 8000으로 낮춰 건당 낭비를 제한했습니다.
- **재검토:** Spring AI가 취소를 전파하게 되거나, 공개 트래픽이 생겨 비용이 문제가 될 때. SDK 스트리밍을 직접 호출하면 해결할 수 있습니다.

### 빈 assistant 메시지를 저장하지 않음

- **이유:** 텍스트 없이 끝난 응답도 빈 메시지로 저장됩니다. Messages API가 이를 거부하면 그 대화의 이후 턴이 모두 실패합니다.
- **근거:** 저장되는 것은 테스트로 확인했습니다. API가 거부하는지는 판단이며 실제로 재현하지는 못했습니다.

### 거부 응답은 `REFUSED` 이벤트로 처리

- **이유:** Spring AI 2.0.2의 옵션으로는 서버 측 `fallbacks`를 지정할 수 없습니다.

## 검색

### 임베딩은 Gemini, 1536차원

- **이유:** Anthropic은 임베딩 API를 제공하지 않아 임베딩만 다른 제공자가 맡습니다. 운영자가 이미 쓰는 Gemini(`gemini-embedding-001`)를 골랐습니다. 출력 차원을 1536으로 지정해 pgvector 테이블과 맞췄습니다. 기본값 3072로 두면 저장이 실패합니다.
- **근거:** 실제 SDK 빈이 보내는 요청(모델, 차원, `x-goog-api-key` 헤더)을 로컬 스텁으로 확인했습니다(`RealBeansStubIT`). 실제 API 호출은 하지 못했습니다.
- **대가:** 키가 두 개(Claude, Gemini) 필요합니다. 임베딩을 로컬 모델로 바꾸면 Claude 키 하나로 되지만 모델 파일과 기동 시간이 늘어납니다.

### 실제 모드 임계값 0.60, Claude 없이 검증하는 `local` 프로필

- **이유:** Claude는 무료 사용량이 없어 검증마다 비용이 듭니다. 답변 모델만 로컬 Ollama(`qwen2.5:7b`)로 바꾼 `local` 프로필을 두고, 같은 검사(`RealModelChecks`)를 `LiveApiIT`와 `LocalModelIT` 두 하위 클래스로 돌립니다. 기본 옵션은 모델 종류에 맞춰 넣습니다. Claude 옵션을 Ollama에 넣으면 Claude 모델 이름이 그대로 넘어가기 때문입니다.
- **근거(실행으로 측정):** 실제 Gemini 임베딩으로 관련 질문 10개의 최저 점수는 0.674, 무관 질문 6개의 최고 점수는 0.531이었습니다. 그 가운데인 0.60을 골랐습니다. 초기값 0.4에서는 무관 질문 6개가 모두 문서 3건씩을 끌고 왔습니다. 같은 실행에서 로컬 모델은 슈트 만재를 열린 질문으로 물었을 때 우회 제안 도구를 골랐고, 인젝션 문장에도 전송은 0건이었습니다.
- **대가:** 로컬 모델의 판단은 Claude의 판단을 대신 증명하지 못합니다. 질문 표본이 16개뿐이라, 문서가 늘면 다시 재야 합니다.

### 임베딩에 메타데이터를 넣지 않음

- **이유:** 해시나 분류 같은 메타데이터가 임베딩 입력에 섞이면, 질문은 원문으로 임베딩하므로 검색 품질이 떨어지고 임계값 보정도 의미를 잃습니다.
- **근거:** 실제 요청 본문에 제목과 본문만 들어가고 해시와 분류가 없는 것을 확인했습니다(`RealBeansStubIT`).

### 해시에 `embedding-index` 포함

- **이유:** 해시가 내용만 보면 임베딩 방식을 바꿔도 옛 벡터가 조용히 재사용됩니다.
- **근거:** 데모와 실제 모드를 오가며 필요한 만큼만 재임베딩되는 것을 확인했습니다.
- **대가:** 데모의 벡터 계산을 바꿀 때는 값을 손으로 바꿔야 합니다.
- **같은 이유로** 임베딩하는 문장 형식(`제목: ...\n내용: ...`)도 해시에 넣습니다. 형식을 바꾸면 전체를 다시 임베딩합니다.

### 빈 지식 문서 파일과 임베딩 실패는 기동 실패

- **이유:** 빈 `[]`를 그대로 처리하면 문서가 모두 지워지고 모든 답변이 "확인할 수 없음"이 됩니다. 조용히 틀린 채 도는 것보다 기동 실패가 낫습니다.

### 데모 임베딩은 단어 안의 글자 2-gram

- **이유:** API 키 없이 실제 검색 경로를 보여 주기 위해서입니다. 측정 결과 공백을 지운 2-gram보다 단어 안 2-gram에 불용어 제거를 더한 방식이 나았습니다.
- **한계:** 의미 검색이 아니며, 무관한 질문이 걸리기도 합니다. [실행과 운영](operations.md)에 사례를 적었습니다.
- **임계값 0.20:** 지식 문서 기준으로 다시 쟀습니다. 정답 질문 10개의 최저 점수는 0.223(알람 101), 무관 질문 31개의 최고는 0.173이라 그 가운데를 골랐습니다. 무관 질문 둘(0.224, 0.236)은 정답 최저보다 높아 어떤 값으로도 정답을 잃지 않고는 거를 수 없습니다. 하나는 단어 일부가 겹치고(다이어트, 컨베이어의 '이어'), 하나는 바이그램 해시 충돌입니다.

## 설비 제어

### 헥사고날 구조

- **이유:** 설비 제조사, AI 모델, 저장소가 각각 바뀔 수 있는데 "무엇을 보내도 되는가"라는 규칙은 바뀌면 안 됩니다. 규칙(`domain`, `application`)이 바깥(`adapter`)을 모르게 해서, 설비를 바꿔도 안전 규칙과 확정 흐름은 그대로 둡니다.
- **근거:** 의존 방향을 `ArchitectureTest`(ArchUnit)가 막습니다. 도구 어댑터는 입력 포트만 부를 수 있고, 들어오는 어댑터 전체가 출력 포트에 의존하지 못합니다(지식 검색 API도 `SearchKnowledge` 입력 포트를 거칩니다).
- **예외:** 출력 포트 `ControlAssistant`와 그 구현 `SpringAiAssistant`는 입력 포트 쪽 `TurnScope`를 받습니다. 턴의 신원과 도구 호출 수는 AI 어댑터를 지나 도구 어댑터까지 가야 하므로 일부러 둔 의존이며, 출력 포트가 입력 포트 타입을 아는 방향이라 위 규칙에는 걸리지 않습니다.

### AI는 제안만, 확정은 사람이 AI 밖에서

- **이유:** 모델은 속을 수 있습니다. 도구가 할 수 있는 일을 "카드 만들기"로 한정하고, 명령은 사람이 `POST /api/commands/{id}/confirm`으로 확정할 때만 나가게 했습니다. 이 경로에는 AI가 없습니다.
- **근거:** 가짜 모델이 모든 설비에 모든 제안 도구를 부르게 해도 설비 전송 0건, 정비 건 0건, 시뮬레이터 상태 불변임을 확인했습니다(`FooledModelIT`). 도구 매개변수에 계정과 권한이 없고, 신원은 서버가 넣은 `TurnScope`에서만 옵니다(`RealBeansStubIT`가 요청 본문으로 확인).
- **대가:** 모든 조치에 클릭이 한 번 더 듭니다.

### 확정 시점에 상태를 다시 비교

- **이유:** 카드를 만든 뒤 현장이 바뀌면 그 카드는 맞지 않을 수 있습니다. 카드에 제안 시점 상태 요약(이산값만)을 저장하고, 확정할 때 다시 읽어 같을 때만 보냅니다. 수치(적재율 등)는 넣지 않아 계속 변하는 값 때문에 확정이 막히지 않게 했습니다. 막힘과 만재는 RUNNING 상태로 보고되므로 따로 넣었습니다.
- **근거:** 막힘 중 만든 우회 카드를 시뮬레이터 리셋 뒤 확정하면 409로 막히는 것을 실제 HTTP와 시뮬레이터로 확인했습니다(`ControlApiIT`).
- **대가:** 상태가 바뀌면 다시 요청해야 합니다. 카드는 2분 뒤 만료됩니다.

### 한 번만 전송, 자동 재시도 없음

- **이유:** 컨베이어 재가동은 두 번 나가면 안 됩니다. 같은 카드를 동시에 확정해도 DB의 조건부 UPDATE와 부분 유일 인덱스가 승자 하나만 남깁니다. 전송 뒤 결과를 확인하지 못하면 다시 보내지 않고 "결과 미확인(UNCONFIRMED)"으로 닫아 현장 확인을 요청합니다.
- **응답 분류:** 연결 전에 실패한 것이 확실할 때(연결 거부, 연결 타임아웃 등)와 4xx(기기의 거절이나 모르는 ID)만 실패(FAILED)입니다. 5xx는 502, 504처럼 게이트웨이나 프록시가 낸 응답일 수 있어 기기가 받았는지 모르므로 읽기 타임아웃, 끊김과 같이 결과 미확인으로 봅니다(`EquipmentHttpTest`).
- **근거:** 실제 PostgreSQL에서 경쟁 상황을 만들어 확인했습니다(`PersistenceIT`). 패자가 유일 인덱스에서 실패해도 같은 트랜잭션의 감사 기록이 남도록 세이브포인트를 씁니다.
- **대가:** 일시적 통신 오류에도 사람이 한 번 더 확인해야 합니다. 전송 중 서버가 죽으면 그 명령은 다음 기동 때 웹 서버가 요청을 받기 전에 UNCONFIRMED로 정리되며, 그 전까지 같은 실행 잠금 키(우회는 분류기 전체, 재배정은 로봇 전체)의 새 명령은 막힙니다.

### 모르면 막는다

- **이유:** 안전 신호가 3초보다 오래됐거나, 설비 상태를 읽지 못하거나, 알람 코드를 모르면 제안을 거절합니다. 판단할 근거가 없을 때 보내는 쪽보다 막는 쪽이 안전합니다.
- **근거:** `SafetyPolicyTest`, `ProposeCommandServiceTest`.
- **대가:** 안전 PLC가 끊기면 아무 조치도 못 합니다. 이 경우는 현장 절차로 넘깁니다.

### 슈트 만재는 두 단계로 조치

- **이유:** CV-3를 바로 재가동하면 원인(CH-03 만재)이 그대로라 다시 멈춥니다. 먼저 우회를 확정하고, 분류기 막힘이 풀린 뒤에 재가동을 제안할 수 있게 했습니다.
- **근거:** 우회 전 재가동은 `SORTER_BLOCKED`로 거절됩니다(`DemoModeIT`, `ControlApiIT`).

### 이벤트는 게이트웨이가 보낸다고 가정

- **이유:** 실제 현장에서는 설비 이벤트를 게이트웨이가 모아 보냅니다. `POST /api/events`는 그 게이트웨이를 대신하는 입구라 인증이 없습니다. 형식(설비 ID, 코드 패턴, eventId)은 검사하고, 장치가 보낸 자유 문자열은 저장하지 않습니다.
- **대가:** 공개 배포 전에는 게이트웨이 인증이 필요합니다.

### 두 번째 어댑터 대신 계약 테스트

- **이유:** "설비를 바꿔도 된다"를 보이려고 제조사 어댑터를 하나 더 만드는 대신, 포트마다 계약 테스트를 두고 메모리 대역과 HTTP 어댑터, JDBC 어댑터가 같은 계약을 통과하게 했습니다. 새 어댑터도 같은 계약을 통과하면 됩니다.
- **근거:** `*Contract` 클래스(설비 4종, 저장소 4종).

### 이벤트 수신과 감지를 분리, 현황 조회는 병렬

- **이유:** 처음에는 이벤트를 받는 요청 안에서 감지를 돌렸습니다. 설비 응답이 늦으면 수신이 3~9초 걸려 시뮬레이터의 3초 전송 타임아웃을 넘었습니다. 감지를 별도 스레드로 넘기고, 현황 조회는 설비군 셋을 동시에 읽게 바꿨습니다.
- **근거(실행으로 측정):** 설비군 셋이 모두 응답하지 않을 때 현황 조회가 약 9.0초에서 약 3.0초로, 같은 조건의 이벤트 수신은 15ms 이하로 줄었습니다.
- **대가:** 감지 작업은 실행 1건과 대기 1건만 두고 나머지는 버립니다. 장애 반영은 최악의 경우 다음 5초 주기까지 늦습니다.

### 도구 호출 수는 직접 센다

- **이유:** Spring AI 2.0.2에도 `spring.ai.tools.limits.max-total-tool-calls`가 있지만, 한 턴 단위로 세고 한국어 고정 문구로 모델에게 알리기 위해 `TurnScope`에서 직접 셉니다(한 턴 8회).
- **한계:** 9~16번째 호출은 `LIMIT_EXCEEDED` 결과로 모델에게 알리기만 합니다. 모델이 이를 무시하고 17번째를 부르면 `TurnScope`가 예외를 던져 스트림이 고정 `error`로 끝납니다(`action`, `done` 없음). 그래서 한 턴의 답변 생성 호출은 최대 17번입니다(후속 질문의 재작성 호출 1번은 별도).
- **세는 위치:** 인자 변환 실패는 도구 메서드 본문 전에 나므로 본문에서 세면 빠집니다. `PlantTools.callbacks()`가 각 콜백을 감싸 변환 전에 세고, 거기서 던진 예외는 `MethodToolCallback`을 거치지 않아 도구 예외 처리기에 잡히지 않고 그대로 턴을 끝냅니다. 형식이 틀린 인자를 계속 보내는 모델도 17번째에서 끊기는 것을 `ToolLoopTest`로 확인했습니다.

### 도구 인자 값을 로그와 결과에 남기지 않음

- **이유:** 모델이 형식이 틀린 인자를 보내면 Spring AI 기본 처리가 그 값을 담은 예외 문구를 도구 결과로 돌려주고 WARN 로그에도 남겼습니다(실행으로 확인). 고정 결과를 돌려주는 `ToolExecutionExceptionProcessor`를 두고 `MethodToolCallback` 로그 레벨을 ERROR로 올렸습니다. 모델이 없는 도구 이름을 부르면 `DefaultToolCallingManager`가 그 이름을 WARN으로 남기므로 이 클래스도 ERROR로 올렸습니다. 같은 실패를 `MessageAggregator`가 예외 문구째 ERROR로 남겨 이 로거는 껐습니다. 끄자 느린 스택 로그에 가려 있던 경쟁이 드러나 오류 직전 청크가 사라졌습니다(`ChatStreamIT` 3회 연속 실패). `SpringAiAssistant`의 `concatMapIterable`이 오류를 받으면 대기 중인 청크를 버리기 때문이라 `concatMapDelayError`로 바꿨습니다. 그리고 스트림 실패와 확정 실패 로그는 예외 클래스 이름만 남깁니다(`ToolLoopTest`, `DecideCommandServiceTest`에서 출력 캡처로 확인).
- **대가:** 이 클래스들의 다른 진단도 보이지 않고, 예기치 못한 실패 로그에 스택과 문구가 없어 원인 추적은 클래스 이름과 카드 ID로 해야 합니다.

## 보안과 설정

### 사용자 입력을 로그에 남기지 않음

- **이유:** 대화와 도구 인자에는 현장 정보나 개인정보가 들어갈 수 있습니다.
- **근거:** 두 경로에서 실제로 새는 것을 확인하고 막았습니다.
  - 입력 검증 실패: `DefaultHandlerExceptionResolver`가 거부된 값을 WARN으로 기록했습니다. 로그 레벨을 올렸습니다(`ChatControllerTest`).
  - NUL 문자 입력: pgjdbc 예외에 전체 메시지가 포함됐습니다. `logServerErrorDetail: false`로 막았습니다(`ChatStreamIT`).
- **오류 로그:** 업스트림 오류 메시지에 입력이나 모델이 만든 도구 이름이 섞일 수 있어 예외는 클래스 이름만 남깁니다(`ToolLoopTest`).

### API 키가 없으면 기동 실패

- **이유:** 프로퍼티 바인딩은 풀리지 않은 `${...}`를 그대로 키 값으로 전달합니다. 실제로 그 문자열이 외부 API로 전송되는 것을 확인했습니다.
- **한계:** 값이 있는지만 확인합니다. 빈 값이나 틀린 키는 잡지 못합니다.

### 범위에서 뺀 것

| 항목 | 추가할 시점 |
|---|---|
| 실제 인증(샘플 계정 대체), rate limit, 대화 소유권, 이벤트 API 인증 | 공개 배포 전 필수 |
| 다중 인스턴스 | 기동 정리와 감지 잠금이 단일 인스턴스를 전제한다 |
| 대화 보존 기간 | 실제 사용자 데이터를 받기 전 |
| Flyway | 운영 DB가 생길 때 |
| hybrid search, reranking | 실제 임베딩으로 측정해 부족할 때 |
